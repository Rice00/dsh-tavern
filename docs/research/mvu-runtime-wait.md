# MVU 运行时接续等待诊断

2026-09-14，年年岁岁正式浏览器游玩路径；原始 10 轮保留，后续在独立分叉诊断。

## 证据

- 原始 10 轮：后台模型完成后额外等待中位数 42.799 秒，接续操作中位数 0.567 秒；首次派发均 queued、claimTimedOut。
- 浏览器可见时仍复现。普通设置请求也出现发送前排队约 48 秒，发送后处理约数毫秒；并非只有 MVU 请求变慢。
- 浏览器领取/心跳请求 3 秒超时；宿主派发 5 秒未被领取便清除 ready 状态，保留待提交结果。后续成功领取或心跳恢复 ready，唤醒接续。没有固定 42.8 秒等待配置。
- 重启前追加两轮仍超时；宿主重启后，同一分叉连续两轮首次派发分别 285ms、217ms 完成，无延后接续。服务端领取请求通常 0–3ms。

## 边界

尚未找到占用请求通道的具体请求或机制。重启同时重置连接、内存并加载全局默认预设配置清理，不能证明具体根因已修复。未验证 70–80 轮，不能外推社区全部性能问题。

## 后续取证

现有诊断导出的性能部分增加 HTTP 慢请求快照：每 5 秒检查一次，只在至少一个请求持续 3 秒以上时记录；保留最近 30 条，最多追踪 256 个并发请求，超出只计数量。仅记录固定请求类别、数量和时间，不记录 URL、查询参数、请求体或响应体。结束、断开及插件卸载均清理监听。

这是进程内诊断，重启清空。它只观察已到服务端的请求，不能直接测量浏览器发送前排队；用于下次故障时比对哪些服务端请求长期未结束。临时逐条控制台日志已清除。

验证：HTTP 诊断、性能摘要、卡片运行时生命周期共 45 项测试通过，客户端构建一致性及语法检查通过。

## 继续取证：连接占用（同日）

使用 Chrome 原生 Network 面板导出时序，并短暂连接 Node 宿主调试器读取 socket 状态，不采集请求内容。确认空闲期 3 个持续请求全部是 `/plugins/events`，来自热更新 SSE；一次 55 秒采样中数量始终为 3，未观察到增长。WebSocket 不按长耗时普通 HTTP 请求统计。

- 浏览器网络记录显示一次 `/api/session/list` 共 7.230 秒（服务器响应前等待约 6.541 秒），`/api/subagents/list` 共 4.652 秒；同时一批生图状态和设置请求在发送前等待约 4 秒。
- 只读重放同一宿主 API，在独立的 6 连接 HTTP/1.1 池中，6 个列表请求并发令随后探测请求等待 471ms；19 个生图状态请求令探测等待 181ms。请求均 HTTP 200；初次未认证的 401 结果已丢弃。这个实验验证当前热态，不能替代旧故障状态或浏览器调度。
- 再追加两轮正式 UI 游玩，MVU 首次派发分别 364ms、535ms 完成，未出现延后接续。同步宿主采样共 271 次；普通 HTTP 最大在途 4 个，峰值为两个 syncSession、两个 getSession；SSE 始终 3 个。采样间隔约 200ms，可能漏掉短请求。

结论：已定位常态长连接和一次较短拥塞中的接口，但尚未复现原来的 42.8 秒等待，也没有证明连接泄漏、静态资源或某个特定接口就是原故障根因。发送前排队是已观察事实，“连接池耗尽”仍是待证机制。旧宿主进程已在上一轮诊断中重启，其内存和连接状态无法从现有记录恢复。

诊断修正：HMR SSE 只作为占用背景保留，不再凭持续时间刷新慢请求记录；列表、会话快照、同步和生图状态接口采用固定类别，避免全部归入 other。新增 SSE 不覆盖真实慢请求的回归测试。
